# A Player's Avatar is a PNG they paint themselves, stored in the database

Until now a Player was shown by their initials only (ADR-0015). Players want a picture, and the
team wants it to be fun rather than a photo upload: an Avatar is painted in the app, on a canvas
with a brush, spray, fill and eraser.

**What is stored.** The full 512×512 square as a PNG, one current image per Player, overwritten on
every save — no history, and removing it is a hard delete back to initials. There is no history
to keep, so a `deleted_at` column (ADR-0004) would only hide a row nobody wants back. The
round shape is only how the image is shown (CSS `border-radius`); the painter draws a circle guide
and dims the corners so the painter knows what will be visible, but never bakes the crop into the
file, so a later shape change needs no re-painting.

**Where it lives.** Bytes go in their own `player_avatar` table (`bytea`), not on `player`, so the
list and detail reads never load them. `player.avatar_updated_at` is the Avatar's version: every
Player read hands it out as `avatarVersion` (epoch millis, or null for initials), and clients load
`GET /api/players/{id}/avatar?v=<avatarVersion>`. A request naming the current version is cached
as immutable; a new save produces a new version and so a new URL. We chose the database over file
or object storage because it's thirteen small images, it keeps backup and the test database
trivially consistent, and there is no storage service in the stack yet.

**Limits.** `PUT` takes `image/png` only: checked by signature, square, at most 512 px and 200 KB;
anything else is a 400. A flat painting is tens of KB; if a spray-heavy one exceeds the cap the
painter saves it at 256 px instead of failing.

**Who may paint.** v1 has no auth, so anyone on a player screen can repaint that Player's Avatar,
same as every other edit in the app.

**Seed.** The seeded Players start with painted Avatars (`V12__seed_player_avatars.sql`): hand-drawn
smileys, some bare, some with hair and doodles. The migration is generated by
`scripts/seed-avatars/draw-avatars.mjs`, which draws them on a real canvas through Playwright;
change the portraits there and regenerate, never by hand-editing the SQL. Being a migration, a
changed portrait needs a new migration rather than a rewritten V12 once V12 has run anywhere.
